阶段2 编排状态图（Supervisor–Worker）

本图严格对应 src/graph/builder.py 的实际节点与边（无装饰节点）。 路由逻辑见 src/agents/supervisor.py::decide_dispatch（纯函数）， 状态合并见 src/graph/state.py（typed reducers，按 id 确定性排序）。 planner 节点先 decompose(query, *, user_context, research_depth) 再调用纯函数 validate_plan：未知依赖 / 重复 task_id / 自依赖 / 依赖环会立即抛 InvalidPlanError，而不是拖到图递归上限。 并发由 max_workers（必须 >0，否则构造期报错）硬上限约束； Send 扇出到 worker 分支并行执行，每个分支经 worker → collector 汇合； 循环由 budget.can_replan()（max_replans）有界。

边与语义（对应 builder.py / supervisor.py）：
• START→planner→supervisor：入口。planner 内部先 decompose(query, *, user_context, research_depth)（统一 Planner 协议，RetryingPlanner 签名一致），再 validate_plan 结构校验；非法计划立即抛 InvalidPlanError。
• supervisor→worker（绿色实线）：Command(goto=[Send("worker", {"task": t}) ...])，每次最多派发 max_workers - running 个无依赖任务。
• worker→collector：每个并行分支结果经 typed reducer 合并（merge_subtasks / merge_facts / merge_citations / merge_errors，按 id 确定性排序、交换律成立；同 task_id 完成优先于失败）。
  - 同 id 不同 payload 冲突：不采用"首次到达赢"，而用 model_dump_json(exclude={extracted_at,fetched_at}) 字典序选稳定 winner（完成优先于失败不变），故 worker 完成顺序不决定结果。
• collector→supervisor（蓝色虚线回环）：仍有可派发任务则继续循环。
• supervisor→collector（黑色虚线）：无可派发任务（槽位满、依赖未满足、或仍有 running 任务）时等待。无 pending 且有 running → wait；无 pending 且无 running（含仅 failed/blocked）→ finish。
• collector→replan：所有任务进入终态。
• replan→supervisor（紫色回环）：证据不足且 budget.can_replan() 为真时追加一个 follow-up 任务，循环有界（max_replans）。
• replan→writer→END：证据足够或重排耗尽，写出报告并结束。
