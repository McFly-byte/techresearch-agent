## 文档维护原则

- **源码优先**：实现状态以 `src/`、`evals/`、`web/src/` 和测试为准。
- **测试佐证**：涉及行为约束时，优先给出对应测试目录或测试文件。
- **区分模式**：明确标注 `fake` 与 `live`，不得把测试数据描述成真实研究结果。
- **区分实现与规划**：尚未接入主流程的组件必须写明“已实现但未接入”或“待实现”。
- **避免易过期数字**：测试数量、依赖小版本和评测成绩应通过命令重新获取，不在知识库中长期固化。
- **保护敏感信息**：不记录真实密钥、令牌、用户数据、完整提示词输入或私有文档正文。

## 与 `docs/` 的关系

- `knowledge-base/`：当前实现、开发约束和交接知识，供持续维护使用。
- `docs/`：保留设计稿、实施记录、演示手册和历史审计材料，其中部分内容可能反映某个历史阶段。
- 根目录 `README.md`：面向首次访问仓库的人，提供最短理解和启动路径。

## 更新检查清单

修改核心代码后，至少检查以下文档是否需要同步：

- 改图节点或状态字段：更新 `02`、`03`、`04`。
- 改环境变量或 provider：更新 `05` 和 `.env.example`。
- 改 API 或 SSE：更新 `06`。
- 改验证/报告策略：更新 `07`。
- 改评测命令或数据格式：更新 `08`。
- 改测试命令或工程门禁：更新 `09`。
- 新增扩展点或重大限制：更新 `10`、`11`、`12`。
